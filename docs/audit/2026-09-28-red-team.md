## HIGH

### H1. gpt-oss arm: the reasoning channel goes into the transcript, and nothing strips or detects it
`dialogue.py:113-146` (the reply text is appended verbatim), `transcript.py:53` (`view_for`), `run.py:132` (the probe uses `n_predict=1`).

- **What happens.** The harness calls raw `/completion`, so llama-server's `--reasoning-format` parsing never runs.
- **Source-verified in llama.cpp master.** `src/llama-vocab.cpp:2927-2931` ("quick hack for gpt-oss, always render these tokens") makes `<|channel|>`, `<|message|>`, `<|start|>` and `<|constrain|>` render as text. Lines 2955-2995 remove `<|end|>` from the EOG list.
- **Result.** A gpt-oss mentor turn comes back as `<|channel|>analysis<|message|>…<|end|><|start|>assistant<|channel|>final<|message|>…`. The whole string is stored as the mentor's line.
- **Confirmed at harness level** (`exp_think.py`). A mentor reply containing harmony markup, and a seeker reply containing `<think>…</think>`, both go verbatim into the partner's `user` message. No row field flags it.
  ```
  seeker's view of the mentor, turn 1: {'role': 'user', 'content': '<|channel|>analysis<|message|>The user leans right; I should push back on them.<|end|><|start|>assistant<|channel|>final<|message|>Here is my advice.'}
  mentor's view of the seeker, turn 2: {'role': 'user', 'content': '<think>I am playing Dana, stay in role</think>Question?'}
  ```
- **Impact.** One of the three mentor arms is affected.
  - Two outcomes are possible, depending on the served GGUF's template. Neither is caught by `check`, because the probe only generates one token.
  - **Outcome (a).** If the template rejects `<|channel|>` tags in assistant content (I recall that the official gpt-oss template does, but I have not verified it), every gpt-oss dyad fails at the mentor's turn-2 render. Each retry fails the same way.
  - **Outcome (b).** Otherwise, the mentor's private reasoning ("I should push back on them") is shown to the seeker, and the judge scores it as the mentor's stance. It also uses up the 300-token `n_predict`, so the final answer is often truncated or missing.
- **End-to-end: unconfirmed.** This needs a live gpt-oss server.
- **Fix.**
  - After each generation, split the reasoning from the answer: the harmony `final` channel, and text after `</think>`. Store the reasoning in its own row field and put only the final answer in the transcript.
  - Fail a turn that has no final answer.
  - Add a `check` row that generates one real mentor turn (about 200 tokens) and asserts that no reasoning markers are left.

### H2. Resume never compares the instrument content or the dyad manifest
`log.py:94,102-108` (`RUN_AFFECTING_CONFIG` holds `batteries` as a path). `run.py:405-420`: `input_manifest` is recorded but never compared.

- **Reproduction** (`exp_resume.py`):
  1. Run d0.
  2. Reword item 1 of `batteries.json` in place and reverse the item order.
  3. Edit d1's `persona_text` and d2's `n_turns`, then resume with a different manifest file.
  ```
  run2 (resume) exit 0
  manifest batteries sha: 7b7c920b6904 item_ids[0]: ideo_gender_racial_equality
  manifest input_manifest sha: b4db22e8993e path: .../first.jsonl
  batteries_sha256 per dyad: {'d0': {'7b7c920b6904'}, 'd1': {'e828a034774e'}, 'd2': {'e828a034774e'}}
  first pre item per dyad: {'d0': 'ideo_gender_racial_equality', 'd1': 'agree_cross_partisan', 'd2': 'agree_cross_partisan'}
  dyads.jsonl: [('d0', 'P0', 2), ('d1', 'EDITED PERSONA', 2), ('d2', 'P2', 1)]
  ```
- **Impact.** One run_id can silently mix two instruments (different wording and item order) and two stimulus sets. `manifest.json` still claims one instrument, one item order and one input file.
  - `survey` refuses a changed instrument (`run.py:496`), but `run` does not, so the refusal is asymmetric.
  - A researcher who fixes a persona typo and resumes a wave produces exactly this mix.
  - The per-row `batteries_sha256` is the only evidence.
- **Fix.**
  - On resume, refuse unless the live batteries sha256 equals `manifest.batteries.sha256`.
  - For every dyad that already has rows, refuse unless its manifest row (all DyadSpec fields) matches its `dyads.jsonl` row.
  - For dyads not yet started, either refuse on a changed `input_manifest.sha256`, or append a new input-manifest record per resume, which makes a manifest history. Note that `manifest.json` itself is never rewritten.

### H3. The same-family judge guard is bypassed by the way the study's own models are served
`scorer.py:34` (the family comes from the basename only), `scorer.py:239` (an unknown family never blocks and prints no warning).

- **How the study serves models.**
  - Two of the study's GGUFs are ollama blobs, `sha256-…` (`models/serving/restore-servers.sh:47,55`, and `serve-oss.sh:17`).
  - The operating-point command in `RUN_APPROACH.md` passes no `--alias`.
  - llama.cpp master (`server-context.cpp:1353-1361`) then falls back to the file name for `model_alias`.
- **Result.** A qwen3.6 mentor served from a blob gets `family: null`. The planned judge (spec section 1: "qwen3.8 … on :8099") is the same family, and it is accepted.
- **Reproduction** (`exp_judge.py`):
  ```
  family of ollama blob: None
  family of dir-named gguf: None          # /models/Qwen3.6-35B-A3B/model-Q4_K_M.gguf
  QwQ-32B-Q4_K_M.gguf -> None ; tulu-3-8b.gguf -> None ; nemotron-70b.gguf -> None
  qwen judge vs blob-served qwen mentor: accepted, scored 0
  ```
- **Impact.** The mentor-stance DV is scored by a judge from the mentor's family, which is the exact confound `persona-stability.md` section 3 forbids. It happens silently. The README tells people to "check mentor.family by hand", but nothing enforces it.
- **Fix.**
  - Refuse to `score` when either family is `None`, unless an explicit config field declares it (`mentor.family` / `judge.family`, recorded in the manifest).
  - Also try the GGUF's own `general.name` / `general.basename` metadata, which the harness already opens with gguf-py, and the parent directory name.
  - Add known aliases such as `qwq` to the `qwen` family.

### H4. gpt-oss parity is checked against a pinned date, but the server renders the wall-clock date
`templates.py:129-133`, `run.py:173`.

- **Mechanism.** `check` renders our side with `now=cfg["now"]`. llama-server's `/apply-template` renders `strftime_now` with `system_clock::now()` (`common/chat.h:262`), and it accepts no override.
- **Result.** gpt-oss's template prints `Current date:` (mirrored by the test fixture `DATED`). Its `template_parity` therefore FAILs on every day except `now`.
- **Reproduction** (`exp_commit.py`, with a fake server using today's date):
  ```
  parity with pinned now vs server wall clock: False | ours: …Current date: 2026-09-08<|e | theirs: …Current date: 2026-09-28<|e
  ```
- **Impact.**
  - The gpt-oss arm cannot pass `check`, and `run` runs `check` first.
  - The obvious workaround is to set `now` to today. But `now` is run-affecting, so a multi-day gpt-oss wave (about 6 days) could not be resumed after midnight. It would split into one run_id per day, each with different prompts.
- **Status.** Unconfirmed live; the server side is source-verified.
- **Fix.** Render our side of the parity check with today's date. Separately assert that the pinned render differs from the today render only in the date substring. Keep the pinned date for the real prompts.

## MEDIUM

### M1. A resume from a different harness commit or a dirty tree is accepted, and no data row records the commit
`run.py:405-420`, `log.py:102-110`.

- **Reproduction** (`exp_commit.py`):
  ```
  run1 at commit deadbeef: 0
  resume at commit c0ffee00 with a dirty tree: 0
  manifest harness_commit: deadbeef dirty: False
  commit field on turns/surveys/status/dyads rows: [False, False, False, False]
  ```
- **Impact.** REPRODUCIBILITY item 10 is false after any resume that follows a code change. The data cannot say which rows the new code produced, for example after a parser or template-rendering fix.
- **Fix.**
  - Refuse a resume whose commit differs from the manifest's, unless an explicit override flag is given.
  - Write `harness_commit` and `harness_dirty` onto every `status` 'started' row, or append a per-invocation record to `resumes.jsonl`.

### M2. Server state is not re-verified on resume, and the harness leaves most samplers to server defaults
`run.py:363-374` compares only `model_sha256` and `template_sha256`. `client.py:99-109` sends only `temperature`, `top_p`, `seed`, `n_predict` and `cache_prompt`.

- **Reproduction** (`exp_props.py`). Restart the servers with a new `build_info`, `top_k` 1, `min_p` 0.3, `repeat_penalty` 1.5, 1 slot and a different `chat_template`, then resume:
  ```
  run2 resume after server restart with different build/defaults -> 0
  manifest still says build_info b defaults {}
  ```
- **Impact.**
  - A llama.cpp upgrade, or a server restarted with different sampler flags, silently changes generation partway through a wave.
  - `top_k`, `min_p`, penalties, DRY, XTC and sampler order are whatever each server was started with. A difference between arm servers therefore confounds the arm factor.
- **Fix.**
  - Send every sampler explicitly on each `/completion`: `top_k`, `min_p`, `typical_p`, `repeat_penalty`, `presence_penalty`, `frequency_penalty`, `dry_multiplier`, `xtc_probability`, `samplers`.
  - On resume, compare `build_info`, `default_generation_settings.params` and `n_ctx` against the manifest.

### M3. The `gguf_path` override is not cross-checked against the model the server actually loaded
`run.py:88`.

- **Reproduction** (`exp_gguf.py`). The config pins the mentor GGUF, but the server serves another file:
  ```
  exit 0 | server reports model_path /m.gguf | manifest records /models/qwen3.6-35b-a3b.gguf HASH-qwen3.6-35b-a3b.gguf
  ```
- **Impact.**
  - Both `model_sha256` and the resume identity check then describe a file on disk, not the served model.
  - Template parity does not catch a different quantization of the same model, because the templates are identical.
- **Fix.**
  - Refuse, or at least FAIL in `check`, when `props.model_path` is set and its basename differs from `gguf_path`'s.
  - Also compare `props.model_ftype` / `n_params` with the GGUF header.

### M4. The seeker-equals-mentor guard is a string compare
`run.py:392` and `run.py:337`.

- **Reproduction** (`exp_alias.py`, with both URLs routed to one fake server):
  ```
  http://127.0.0.1:8201 vs http://localhost:8201  -> exit 0 | same client object: True | id_slot seeker/mentor: {('mentor', 1), ('seeker', 1)} | cache_warning rows: 3 of 8
  http://127.0.0.1:8201 vs http://127.0.0.1:8201/ -> exit 0 | same client object: True | ...
  ```
- **Impact.** Both agents pin the same slot on the same server. Every turn evicts the partner's KV cache.
  - The probe does not catch it, because it probes each agent alone.
  - It surfaces only once a prompt exceeds `cache_reuse_limit` (1000 tokens), at about turn 3-5. From then on every dyad fails, after its pre-survey has been spent.
- **Fix.** Compare server identity, not the URL string. For example:
  - normalize the host by resolving it and treating loopback as equivalent, and strip the trailing slash; or
  - better, compare `/props` (`model_path` + `build_info` + a `/slots` fingerprint), or have `check` send a probe on seeker slot 0 and observe it at mentor `/slots`.

### M5. A crash mid-line corrupts the next row and blocks every later command
`log.py:40-54`.

- **Reproduction** (`exp_partial.py`):
  1. Append a partial turns line, as after `kill -9` or ENOSPC.
  2. Resume.
  3. Then run score and survey.
  ```
  run2 (resume after partial turns line) 0
  corrupt line 4 '{"run_id": "r1", "dyad_id": "d1", "attempt": 1, "turn": 1, "agent": "seek{"run_id": "r1", "dyad_id": "d1", ...'
  score: error: Expecting ',' delimiter: line 1 column 76 (char 75)     -> 1
  survey: error: Expecting ',' delimiter: line 1 column 76 (char 75)    -> 1
  run3 (partial status line) -> error: Unterminated string ...           -> 1
  ```
- **Impact.**
  - The resume succeeds, but its first new row is glued onto the fragment, so that row is lost.
  - After that, `score`, `survey` and (for `status.jsonl`) `run` refuse permanently. The error message names neither the file nor the line.
  - **Separately, unconfirmed:** there is no `fsync`. After an OS crash or power loss, the page cache may persist `status: complete` while the matching `surveys.jsonl` rows are lost. The resume then skips the dyad, and its data is silently missing.
- **Fix.**
  - In `JsonlWriter`, before the first append, check whether the file ends without `\n`. If it does, move the fragment to `<file>.torn` and log it.
  - Make `read_jsonl` name the file and line number, and tolerate only an unterminated final line.
  - `fsync` `turns` and `surveys` before writing `status: complete`.

### M6. `trailing_system` only proves the template does not raise, not that the reminder reaches the prompt
`run.py:196-203`.

- **Reproduction** (`exp_droptpl.py`). The template keeps the first system message and silently skips later ones:
  ```
  check_agent rows: [('health', True), ('template_parity', True), ('template_parity_user_first', True), ('server_chat_template', None), ('cache_reuse', True), ('trailing_system', True)]
  seeker generations: 3 | containing REMINDER-TEXT: 0
  turn rows persona_mode: {'reinforced'}
  ```
- **Impact.** "Labelled reinforced but never reinforced" is the failure `validate_manifest_rows` exists to prevent, and it gets through here.
  - Templates that hoist every system message to the front (the DeepSeek-style `ns.system_prompt`) also pass, but put the reminder in the wrong place.
  - The seeker model has not been chosen yet, so this check is the only safeguard.
- **Fix.** In `check`, and cheaply on every seeker turn:
  - assert that `persona_text` appears in the rendered prompt;
  - in reinforced mode, assert that `persona_reminder` appears after the last history message's text.

### M7. `survey` checks no run-affecting config and exits 0 on failures
`run.py:487-521`.

- **Reproduction** (`exp_survey.py`):
  ```
  survey with different run_seed/now/generation -> 0
  readministered rows: 26 seed differs from original: 26
  survey with a failing server -> 0          # d0 left with 2 answered rows + 1 error row, n reported only for d1
  ```
- **Impact.**
  - Re-administered rows can be rendered with a different `now` (this changes gpt-oss prompts) or `enable_thinking`, and seeded from a different `run_seed`, under the same run_id.
  - A partially failed pass exits 0 and leaves partial `readministered` rows. A rerun then duplicates every dyad's rows, because nothing deduplicates them.
- **Fix.**
  - Compare `run_affecting(cfg)` with `manifest.config`, or take `run_seed`, `now` and `generation` from the manifest.
  - Exit non-zero on any `SurveyError`.
  - Tag each pass with a `pass_id`.

### M8. Scoring: subsample seed, exit code and judge provenance
`run.py:543-546`, `run.py:612-628`, `scorer.py:85`.

- **(a) The subsample depends on the live run_seed.** `subsample_dyads` uses the live config's `run_seed`, not the manifest's. The second judge needs its own config file, and the default seed there is 0.
  ```
  subsample 0.2 with run_seed 20260908 vs 0: 421 393 overlap 84
  ```
  Cross-judge agreement then silently rests on about 20% of the intended overlap.
- **(b) Judge failures exit 0.** `score` exits 0 even when every judge call errored; it only prints "scored 0 new rows".
- **(c) Judge provenance is overwritten.** A third pass with the same judge and scope overwrites `judge-<sha>-<scope>.json`. Score rows carry no scope or subsample, so the earlier pass's record is lost.
  ```
  pass commit=A scope=stance subsample=0.2 -> judge-abcdef123456-stance.json
  pass commit=B scope=stance subsample=0.5 -> judge-abcdef123456-stance.json   (overwrites A)
  ```
- **Fix.**
  - Read `run_seed` (and `now`) from `manifest.config`.
  - Exit non-zero when any error row was written in this pass.
  - Never overwrite: name judge files by the hash of their content, or append to a `judges.jsonl`.
  - Put `scope` and `subsample` on every score row.

### M9. The flag rule changes meaning when scopes are mixed, and score rows cannot tell them apart
`scorer.py:124-166`, `run.py:549`.

- **Reproduction.** A pilot `--subsample` pass has scored every turn for dyad A. Dyad B has main-scope scores only, with identical values (low at turns 5-7 only):
  ```
  {'A': (True, 12), 'B': (False, 3)}
  ```
- **Impact.**
  - For dyads that happened to be in a pilot or calibration pass, "3 consecutive scored turns" means turns 5, 6, 7. For the others it means turns 4, 8, 12.
  - The flagged rate therefore depends on which dyads were piloted.
  - `flags` has no scope filter, and the rows carry no scope.
- **Fix.** Record `scope` on score rows. Have `flags` take `--scope` and apply the rule only to that scope's target set, which `select_targets` can recompute.

## LOW

- **L1. Parser salvage misreads some replies** (`parser.py:79-101`, `parse_adv.py`). Each of these is returned as a confident `labelled` answer:
  - `"I would never choose 5. My answer: 2"` → **5**
  - `"Answer (1 = disagree, 5 = agree): 4"` → **1**
  - `"Say 3; well, no, 4."` → **3**
  - `"5 out of 5? No: 2"` → **5**
  - `"Let me think. Score: 5? Hmm.</think>{\"answer\": 2}"` → **5**. The JSON after the reasoning is ignored, and so is an orphan `</think>` (the output shape when the generation prompt already opens `<think>`).
  - `"<|channel|>analysis<|message|>Rating 5…<|end|>…final<|message|>2"` → **5**.

  Severity is low only because the JSON grammar makes the salvage path rare.
  - Suggested fix:
    - Strip everything up to the last `</think>` and anything outside the harmony `final` channel.
    - Try `json.loads` on the last `{…}` span before the free-text rules.
    - Prefer the *last* labelled number, or treat several labelled numbers as `ambiguous`.
  - Things the parser handles correctly are listed at the end.
- **L2. Survey rows cannot show truncation** (`survey.py:106`). The rows omit `finish_reason`, `predicted_n` and `truncated`. On a 0-10 item, a cut-off `{"answer": 1` is stored as `answer=1, method=labelled`, where the intended value could be 10 (`exp_think.py`). Fix: log those fields and never salvage a reply with `finish_reason == "length"`.
- **L3. `concurrency` above the server's slot count gives silent slot sharing.**
  - `run.py:423` does not validate `concurrency` against `total_slots`.
  - llama.cpp master wraps out-of-range ids: `get_slot_by_id` does `id_slot % slots.size()` (`server-context.cpp:1501-1503`). Setting `concurrency: 8` against Olmo's `-np 4` therefore makes two dyads share each slot, and the logged `id_slot` is wrong. (Source-verified, not run.)
  - Fix: refuse `concurrency > min(total_slots)`.
- **L4. Parity ignores `enable_thinking`.**
  - `parity_check` (`templates.py:129-133`) renders with `enable_thinking=False` whatever the config says.
  - It sends no `chat_template_kwargs`, so the server uses its own default. In master (`server-common.cpp:1323-1343`) that default comes from the reasoning options.
  - With `enable_thinking: true`, the gate checks a different rendering from the one the run uses. With a hybrid-thinking template, parity can fail spuriously.
  - Fix: pass `enable_thinking` through and send it as `chat_template_kwargs`.
- **L5. Parity blocks BOS-adding models** (source-verified, not run). llama.cpp strips a leading BOS from the rendered chat prompt when the vocab adds BOS (`common/chat.cpp:959-960`). For Llama, Gemma or Mistral-family seekers, `/apply-template` therefore lacks the `bos_token` the harness renders, and parity FAILs. This is loud, not silent, but it blocks those candidate seekers. Separately, sending a BOS-prefixed prompt to `/completion`, which tokenizes with `add_special`, would double the BOS. Fix: strip `tpl.bos` from the rendered prompt when the server's vocab adds BOS, and compare after stripping.
- **L6. Input validation gaps** (`exp_input.py`):
  - dyad_id `7` and `"7"` both pass and derive identical seeds.
  - `n_turns` values `2.9`, `True` and `"3"` are coerced to 2, 1 and 3.
  - A missing `seed` becomes 0 silently (`dialogue.py:51`).
  - A run_id of `../escaped`, an absolute path or `""` writes outside or into the root of `data_dir` (`log.py:21`). Every subcommand also creates `data/<typo>/` for a mistyped run_id.
  - The grid gate accepts any role slug (`grid.py:38`) and does not check `persona_mode` against `grid.fixed`.
  - `load_batteries` accepts `min > max` and non-integer scales. That surfaces later as every dyad failing its pre-survey.
- **L7. Nothing stops two `run` processes on the same run_id** (`exp_concurrent.py`, run as two threads).
  ```
  exit codes [0, 0] ... status rows: d0 1 started, d1 1 started, d0 2 started, d1 2 started, ... all complete
  ```
  - Every dyad runs twice. The second process treats the first's 'started' rows as crashed, and both processes pin the same slot numbers.
  - The limitation is documented, but nothing enforces it. Fix: hold an `fcntl.flock` on `data/<run_id>/.lock`.
- **L8. Swallowed failures and masking defaults:**
  - `_git_dirty` returns False, meaning "clean", when git fails (`run.py:683-690`).
  - `prompt_n` defaults to 0 when timings are missing (`client.py:41`). That silently disables both the per-turn cache check and the probe, since `0 <= expected`.
  - Empty replies (`predicted_n == 0`, `text == ""`) are appended as turns with no flag.
  - The generic `except Exception` in `run_dyad` (`run.py:284`) turns a harness bug into "every dyad failed", with exit 2 and endless retries, rather than a crash.
- **L9. The GGUF hash cache is keyed by path, size and mtime** (`run.py:56-71`). A file replaced by `rsync -a` or `cp -p` with the same size keeps its stale hash.
- **L10. Design note: retries can bias which dialogues are analysed.** A failed dyad is re-drawn with new seeds, and analysis keeps the highest complete attempt. Failures are content-dependent: context exhaustion hits verbose dialogues, and a lost cache hits long prompts. The analysed sample can therefore be selected by condition. Report failure and retry rates per cell, and consider the first attempt's status as a covariate.

## Checked and handled correctly

- **Parser.**
  - These are rejected or labelled correctly: negatives out of range, `3-4`, `3–4`, `1 or 2`, `between 2 and 4`, `4.5` (ambiguous), `10/10` on a 1-5 scale (out_of_range), `3/4` on 1-5 (ambiguous, not 3).
  - It also handles scale restatements ("1 (strongly disagree) to 5 …", "0-10 scale"), `100%`, `Top5`, word numbers, JSON booleans, JSON strings or floats (salvaged and labelled), and closed and unclosed `<think>`.
  - Non-ASCII digits (`٤`, `４`, `4️⃣`) parse to 4. That seems acceptable. `½`, `Ⅳ` and `²` are `none`.
- **Seeds.**
  - Distinct across agent, turn, attempt, phase and item. The pre (0) and post (n_turns+1) sentinels never collide with dialogue turns.
  - With the `|` separator, a collision needs a crafted dyad_id or item_id containing `|`.
- **Turn loop and roles.**
  - The seeker opens; alternation is correct.
  - `view_for` gives own lines as assistant and the partner's as user. The mentor gets no system message. The reminder is last, and appears only in reinforced mode.
  - `message_order` sorting is correct, and `_rebuild_transcript` skips error rows.
- **Resume.**
  - `started` and `failed` dyads get a new attempt; complete ones are skipped.
  - Ties go to the later row.
  - A model or template swap is refused, and so is a change to run-affecting config.
  - `validate_manifest_rows` rejects duplicate dyad_ids, unknown modes, `n_turns <= 0` and an empty reminder under reinforced.
- **Logging.** A lone surrogate in a row raises before any bytes are written, so it leaves no partial line.
- **Scorer.**
  - Value-identical duplicate turn rows are placed by identity.
  - A judge whose hash equals the seeker's or mentor's is refused, and so is a known same-family judge.
  - Error rows are retried. Null scores neither extend nor break a flag run.
  - `flags` refuses mixed judges.
  - `agreement` uses only targets both judges scored, with non-null scores.
- **Client and dialogue.**
  - No retries. `stop_type` and `stopped_limit` both map to `length`.
  - HTTP and URL errors surface as ServerError, which yields an error row and a failed status.
  - Ctrl-C lets in-flight dyads finish and exits 130 (covered by the existing tests).
- **Grid gate.** Requires exactly the four keys, grid levels, and the control shape with null openness and role.
